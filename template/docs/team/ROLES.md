# Роли команды

Шесть ролей на шесть человек. Если людей меньше, один человек берёт две соседние роли
(например, `qa` + `content` или `design` + `frontend`). Роль задаёт зону ответственности,
а не запрет помогать: можно брать любые задачи, но в чужой зоне правки согласуются.

| Роль | Кто это | Зона (пример для веб-проекта) | Главный результат |
| --- | --- | --- | --- |
| `lead` | Владелец, интегратор | `.github/`, зависимости, миграции, `CLAUDE.md` | Рабочий `main` в любой момент |
| `frontend` | Интерфейс | `src/components/`, стили, страницы | Экраны для демо |
| `backend` | Сервер и данные | `api/`, `supabase/`, интеграции | Работающие запросы и данные |
| `content` | Контент и данные | `src/data/`, тексты, промпты моделей | Содержимое, которое видит пользователь |
| `qa` | Качество | `test/`, проверки CI, сценарии демо | Ничего не ломается на демо |
| `design` | Дизайн и подача | `docs/`, `README.md`, презентация, иконки | Питч, демо-видео, README |

Зоны для вашего проекта впишите в раздел «Проект» ниже и в `.github/CODEOWNERS`.

## lead — владелец

- Режет идею на задачи по 1–4 часа и раздаёт их (`scripts/team.sh task`).
- Единственный сливает в `main` (`scripts/team.sh merge`). Сливает часто и маленькими
  кусками: каждый час `main` должен собираться.
- Делает задачи с меткой `shared`: зависимости, lock-файл, миграции, общие настройки.
- Раз в 2–3 часа: `scripts/team.sh board`, разблокировать застрявших (`status:blocked`).
- Хранит ключи у себя и раздаёт участникам лично (менеджер паролей, личное сообщение),
  никогда через репозиторий, задачи или PR.

## frontend

- Экраны и компоненты. Сначала «скелет» с заглушками данных, чтобы не ждать backend.
- Договаривается с backend о форме данных в задаче до начала работы.

## backend

- API, база, внешние сервисы. Первым делом — форма ответов (контракт) в задаче,
  чтобы frontend мог работать параллельно на заглушках.
- Новые переменные окружения: только имя в `.env.example`, значение у владельца.

## content

- Тексты, данные, промпты, словари. Работает в файлах данных, а не в коде компонентов.
- Проверяет, что контент проходит проверки проекта (например, тесты корпуса).

## qa

- Пишет тесты на критичный путь демо, следит за CI, проверяет PR по шагам «Как проверить».
- За 4 часа до конца ведёт прогон сценария демо и заводит баги с меткой `demo`.

## design

- Внешний вид, иконки, README, презентация, демо-видео.
- К концу хакатона отвечает за питч: проблема → решение → живое демо → что дальше.
